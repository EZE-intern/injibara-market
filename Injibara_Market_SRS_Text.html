01 Introduction

1.1 Purpose

This Software Requirements Specification (SRS) establishes the formal functional and non-functional requirements for the Injibara Market software system. It documents the functional scope, behavioral contracts, database schemas, access control models, and performance targets governing the development, deployment, and academic defense of the platform.

1.2 Scope of the System

Injibara Market is a full-stack, cloud-native web marketplace tailored specifically to the regional trade conditions of Injibara town and the surrounding Awi administrative zone. The platform introduces a structured Two-Tier Transaction Model designed to resolve trust and verification deficits:

  • Tier 1: Brokered Capital Marketplace: High-value physical assets (Real Estate, Land Plots, Farm Holdings, Automobiles, Bajajs, Trucks, and Heavy Agricultural/Construction Machinery). Buyer inquiries on these items bypass direct seller contact and route strictly to the municipal Admin Broker Desk. The platform admin authenticates buyer intent, coordinates physical inspections, and contacts the seller directly via telephone.
  • Tier 2: Direct Consumer Marketplace: Standard retail and consumable goods (Electronics, Fashion, Processed Foods, Farm Produce, Furniture, Household Goods). Buyers communicate directly with verified merchants through real-time in-app threaded chat.

02 Overall Description

2.1 Product Perspective & Runtime Architecture

The system operates on an asynchronous, decoupled client-server architecture deployed across cloud services:

  • Client Tier: Single-Page Application (SPA) built on React 19, Vite 8, and Tailwind CSS 4, deployed on Vercel's Edge CDN with URL rewriting (/* → /index.html).
  • Application Tier: Node.js 20 ESM runtime hosting Express 5. Implements three-tier rate limiting, Zod schema coercion, Multer zero-disk RAM streaming, and the Prisma 7 MariaDB driver adapter.
  • Data Persistence Tier: TiDB Cloud Serverless instance deployed in AWS Frankfurt (eu-central-1), providing distributed ACID transactions and TLS-encrypted connectivity.
  • Media Storage Tier: Cloudinary object cloud, receiving binary byte streams piped directly from Node RAM buffers, delivering auto-negotiated WebP/AVIF formats to clients.

03 Specific Functional Requirements

3.1 Authentication & Account Management (AUTH)

  • FR-AUTH-01 (User Registration): The system shall register users with full name, unique email, password, optional phone number, and requested role (customer or seller). Admin role requests via registration payload shall be strictly rejected.
  • FR-AUTH-02 (Phone Sanitization): The system shall validate Ethiopian phone numbers against regex /^(?:\+?251|0)(9|7)\d{8}$/ and normalize all variants into canonical 10-digit format (09xxxxxxxx or 07xxxxxxxx).
  • FR-AUTH-03 (Password Hashing): Passwords shall be cryptographically transformed using bcrypt (salt factor 10). Plaintext passwords shall never be persisted or logged.
  • FR-AUTH-04 (Stateless JWT Issuance): Upon valid authentication, the server shall issue an HMAC-SHA256 signed JWT containing { id, role, email } with a 30-day expiration window.
  • FR-AUTH-05 (Admin Bootstrap Whitelist): Registrations whose email matches the INITIAL_ADMIN_EMAILS environment variable shall be automatically promoted to admin upon creation.
  • FR-AUTH-06 (Self-Demotion Guard): The system shall forbid an active administrator from revoking their own admin privileges.

3.2 Product Catalog & Inventory (PROD)

  • FR-PROD-01 (Product Publication): Authorized sellers shall create listings with: name, description, price (ETB), optional discount price, inventory count, category ID, location, and up to 6 image files.
  • FR-PROD-02 (Discount Logic Integrity): The system shall assert that discount_price < price using cross-field schema refinement.
  • FR-PROD-03 (Zero-Disk Upload): Uploaded image files (JPEG, PNG, WebP; max 5MB) shall be buffered in memory and streamed directly to Cloudinary via streamifier without writing to local server disk.
  • FR-PROD-04 (Auto Seller Promotion): A customer publishing their first product listing shall be automatically promoted to the seller role.
  • FR-PROD-05 (Soft Deletion): Product deletions shall update deleted_at = NOW() and is_active = false to maintain historic order integrity.
  • FR-PROD-06 (Catalog Discovery): Public listings shall support category filtering, keyword search, location filtering, and cursor-based pagination.

3.3 The Two-Tier Broker Subsystem (BRK)

  • FR-BRK-01 (Tier Evaluation): When a buyer initiates an inquiry, the server shall test the category against 22 regex rules covering English and Amharic keywords (Property, Land, Vehicles, Machinery, መሬት, መኪና, ባጃጅ, ማሽነሪ).
  • FR-BRK-02 (Tier 1 Broker Dispatch): For Tier 1 matches, message recipient resolution shall target the primary broker (seberbel@gmail.com). The product seller shall receive zero in-app messages.
  • FR-BRK-03 (Tier 2 Direct Dispatch): For non-brokered categories, messages shall route directly to the listing seller's inbox.
  • FR-BRK-04 (Broker Pipeline Tracking): Tier 1 deals shall create/update a record in broker_inquiries, progressing across five lifecycle states: NEW → ASSIGNED → APPOINTMENT_SCHEDULED → MEDIATED → CLOSED.
  • FR-BRK-05 (Appointment Scheduling): Administrators shall be able to record physical property inspection timestamps (appointment_date) and mediation notes.
  • FR-BRK-06 (Message Deduplication): Admin responses to buyer inquiries shall update the existing inquiry thread rather than generating redundant pipeline items.

3.4 Shopping Cart & Checkout (ORD)

  • FR-ORD-01 (Persistent Cart): Authenticated customers shall add, modify, and delete cart items with database synchronization.
  • FR-ORD-02 (Atomic Stock Transaction): Order placement shall execute within an interactive database transaction (prisma.). The engine shall verify available stock, decrement inventory, generate the order record, and create line items. If any item lacks stock, the entire transaction rolls back.
  • FR-ORD-03 (Order Tracking Number): Orders shall generate a unique identifier formatted as ORD-{TIMESTAMP}-{RANDOM}.
  • FR-ORD-04 (Payment Channel Selection): The checkout workflow shall accept: Telebirr, CBE Birr, Bank Wire, or Cash on Delivery.
  • FR-ORD-05 (Seller Order Fulfillment): Sellers shall access a dedicated fulfillment view displaying orders containing items from their inventory with customer contact information.

3.5 In-App Communication (MSG)

  • FR-MSG-01 (Threaded Conversations): Messages shall be grouped into threads organized by contact ID and product reference.
  • FR-MSG-02 (Unread Counters): The server shall provide an endpoint returning aggregate unread messages where receiver_id == user.id and is_read == false.
  • FR-MSG-03 (Auto-Read Acknowledgment): Opening a conversation thread shall mark all incoming messages as read.

3.6 Administrative Governance (ADM)

  • FR-ADM-01 (Platform Telemetry): The admin overview dashboard shall report platform totals: registered users, active listings, order counts, and transacted gross volume (ETB).
  • FR-ADM-02 (Listing Moderation): Administrators shall approve, reject (with mandatory reason), or archive product listings.
  • FR-ADM-03 (Store Governance): Admins shall activate or suspend merchant store profiles.
  • FR-ADM-04 (User Sanctioning): Admins shall toggle user account active status, preventing suspended users from signing in or transacting.
  • FR-ADM-05 (Staff Administration): Admins shall provision, configure, and revoke staff admin accounts.

05 Non-Functional Requirements

5.1 Performance & Cold-Start Resilience

  • NFR-PERF-01 (Response Time): Under warm server conditions, 95% of read requests shall resolve within 350ms; database writes shall commit within 800ms.
  • NFR-COLD-01 (Extended Client Timeout): Due to serverless compute container wake-up delays (20–35s), the client Axios instance shall implement an extended timeout window of **60,000ms (60 seconds)**.
  • NFR-COLD-02 (Exponential GET Retry): Read operations encountering connection timeouts, socket drops, or 502–504 gateway failures shall automatically retry up to 2 times with exponential backoff (1.5s, then 3.0s).
  • NFR-COLD-03 (Proactive Wakeup Ping): The root application component shall trigger a non-blocking background ping to /healthz on mount to initialize server container wake-up.
  • NFR-COLD-04 (Resilient Error UI): Network failures shall render informative error alerts featuring a manual "Retry" trigger rather than silently failing to an empty listing state.

5.2 Security & Data Integrity

  • NFR-SEC-01 (RBAC Verification): Protected administrative routes shall enforce a two-stage middleware check: JWT signature verification followed by role authorization. Unauthorized requests shall be rejected with HTTP 403 Forbidden.
  • NFR-SEC-02 (Three-Tier Rate Limiting):
    • Global API: 300 requests per 15-minute rolling window per IP.
    • Auth Routes (/login, /register): 10 requests per 15-minute window per IP.
    • Content Creation (POST /products, POST /messages): 25 requests per 15-minute window per IP.
  • NFR-SEC-03 (Input Sanitization): All input bodies shall be coerced and validated through Zod schemas before reaching controller logic.
  • NFR-SEC-04 (Atomic Inventory): Inventory decrementing must be executed in a database transaction to prevent overselling under high concurrency.

5.3 Usability & Localization

  • NFR-USA-01 (Bilingual Security Feedback): Authentication error messages shall be rendered in Amharic (e.g., ያልተፈቀደ መዳረሻ፣ ቶከን አልተገኘም).
  • NFR-USA-02 (Toast Deduplication): Notification dispatchers shall suppress identical error toasts within a 5-second window to prevent notification spam during network interruptions.

6.2 Ethiopian Phone Number Normalization Algorithm

Algorithm: NormalizeEthiopianPhone(raw_input: string) -> string:
  1. Remove all whitespace, hyphens, parentheses: sanitized = raw_input.replace(/[\s\-\(\)]/g, '')
  2. If sanitized starts with '+', remove '+': sanitized = sanitized.slice(1)
  3. If sanitized starts with '251', replace with '0': sanitized = '0' + sanitized.slice(3)
  4. If sanitized length == 9 and starts with '9' or '7': sanitized = '0' + sanitized
  5. Validate against regex: /^(09|07)[0-9]{8}$/
  6. Return canonical 10-digit format (e.g., '0911223344')

6.3 Two-Tier Broker Category Classification Algorithm

Algorithm: IsBrokeredCategory(category_name: string, category_slug: string) -> boolean:
  1. Combine test target: target = (category_name + ' ' + category_slug).toLowerCase()
  2. Rule 1 (Property): /land|property|real.?estate|house|plot|farm.?land|ቦታ|መሬት|ቤት/i
  3. Rule 2 (Vehicles): /vehicle|car|truck|tractor|motorcycle|bajaj|auto|መኪና|ባጃጅ|ሞተር/i
  4. Rule 3 (Heavy Machinery): /machinery|equipment|generator|harvester|ማሽነሪ|ትራክተር/i
  5. If target matches Rule 1, 2, or 3:
       Return TRUE  -> Route to Admin Broker Desk (seberbel@gmail.com)
     Else:
       Return FALSE -> Route directly to Seller Inbox
