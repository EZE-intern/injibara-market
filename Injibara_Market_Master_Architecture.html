1.3 Architectural Patterns & Design Paradigms

The Injibara Market codebase intentionally adopts six structural design patterns to ensure reliability, separation of concerns, and type-safety:

  • Layered Architecture (Controller-Model-Route Separation): Routes declare URL topologies and attach middleware chains; controllers handle HTTP orchestration and business rules; models wrap specialized Prisma queries; Prisma models map physical database entities.
  • Driver Adapter Pattern (Prisma 7): Instead of bundling Prisma's heavy Rust-based native query engine binary, the server uses @prisma/adapter-mariadb. This adapter executes queries via the pure JavaScript/C++ mariadb driver, significantly shrinking the deployment footprint and cold-start overhead.
  • Middleware Pipeline (Chain of Responsibility): Express middleware chains enforce orthogonal concerns sequentially: Rate Limit → Authentication → RBAC Authorization → Multer RAM Ingestion → Zod Schema Validation → Controller Execution.
  • Zero-Disk Stream Pipelining: Multer stores files strictly in memory buffers, while streamifier adapts raw memory into NodeJS Readable streams to pipe directly into Cloudinary's TLS socket. No temporary file cleanup or inode leaks can occur.
  • Client Interceptor Facade: axiosClient.ts encapsulates token injection, session expiration redirects, proactive server cold-start pinging, exponential retry backoff for network drops, and toast notification throttling.
  • Native Browser Event Bus: Real-time cross-component synchronization (e.g., updating wishlist badges across disparate components) uses native browser CustomEvents (saved_products_updated), eliminating unnecessary global state libraries.

03 Data Layer, TiDB Handshake & Prisma Engine

3.1 TiDB Serverless Internals vs. Traditional MySQL

Although the application connects to TiDB using the standard MySQL wire protocol, the underlying database engine is fundamentally different from a monolithic MySQL 8.0 instance:

  • Separation of Compute and Storage: The TiDB stateless SQL layer (compute) receives queries, validates permissions, and compiles SQL parse trees into distributed execution plans. It does not store physical table pages.
  • Distributed Storage Engine (TiKV): Data is stored in distributed key-value storage engines called TiKV. Tables and indexes are partitioned into continuous key-range segments called Regions (typically 96MB in size), replicated via the Raft consensus algorithm across multiple availability zones.
  • Placement Driver (PD): Acts as the cluster brain, managing Raft group allocations, region rebalancing, and global timestamp allocation (TSO) for multi-version concurrency control (MVCC).
  • Behavioral Implications for Injibara Market:
    1. Latency Profile: Because cross-node network hops and Raft consensus are required for write commits, single-row INSERT/UPDATE operations have higher base latency (~30-60ms) than local MySQL (~1-2ms), but horizontal scalability and fault tolerance are substantially superior.
    2. Serverless Sleep Mode: TiDB Serverless clusters scale to zero when idle to conserve cloud credits. The first query after an idle window incurs a compute-node spin-up delay (hence the frontend's 60s timeout and exponential backoff retry).

3.4 Atomic Transaction Mechanics: Stock Validation and Deduction

When an order is created, the system must guarantee that inventory cannot be oversold under concurrent traffic. The orderController.createOrder function executes inside an atomic Prisma interactive transaction (prisma.$transaction): 

// Atomic transaction execution in server/src/controllers/orderController.ts
const newOrder = await prisma.$transaction(async (tx) => {
  // 1. Create the parent order record
  const created = await tx.orders.create({
    data: {
      user_id: userId,
      order_number: orderNumber,
      total_amount: totalAmount,
      status: 'pending',
      payment_method: payment_method || 'cash_on_delivery',
      payment_status: 'pending',
      shipping_address: shipping_address || null,
      order_items: { create: orderItemsData },
      order_status_history: {
        create: { status: 'pending', changed_by: userId },
      },
    },
    include: { order_items: true },
  });

  // 2. Atomically deduct inventory for every purchased product
  for (const p of productsToUpdate) {
    await tx.products.update({
      where: { id: p.id },
      data: { stock: p.newStock },
    });
  }

  return created;
});

If any single product update fails or if a network disconnect occurs mid-loop, TiDB rolls back the entire transaction, guaranteeing no orphaned order items or desynchronized stock levels.

3.5 Zod Validation Pipeline

The server rejects invalid data before controllers are invoked. A dedicated factory middleware validate(schema) parses req.body against Zod schemas in src/schemas/index.ts:

  • Ethiopian Phone Number Normalization: Strips formatting characters, validates against /^(?:\+?251|0)(9|7)\d{8}$/, and normalizes inputs to canonical 09xxxxxxxx or 07xxxxxxxx format.
  • Sanitized Emails: Lowercases and trims all email strings, preventing casing-based account duplication.
  • Discount Logic Refinement: The product schema applies a cross-field .refine() assertion guaranteeing that discount_price < price.
  • Role Escalation Defense: The registration schema restricts incoming roles to customer or seller only; any attempt to supply admin is stripped at parse time.

04 Security, Authentication & Session Boundaries

4.1 Cryptographic JWT Lifecycle

Authentication relies on stateless JSON Web Tokens signed with HMAC-SHA256:

  1. Password Hashing: During registration, raw passwords undergo one-way hashing via bcryptjs with a salt work factor of 10 (bcrypt.genSalt(10)), generating a 60-character bcrypt hash.
  2. Token Issuance: Upon credential verification, generateToken.ts constructs a signed JWT payload: 
    { "id": user.id, "role": user.role, "email": user.email, "exp": Date.now() + 30d }
  3. Secret Management: Tokens are signed using JWT_SECRET loaded from environment variables, backed by a safety fallback constant to guarantee system continuity.
  4. Storage & Delivery: The client stores the token in localStorage under injibara_market_token and attaches it as an HTTP header: Authorization: Bearer <token>.

4.3 Multi-Tier Rate Limiting Strategy

To prevent resource exhaustion and brute-force credential stuffing, three distinct rate limiting policies are enforced via express-rate-limit:

  • Global Guard (globalLimiter): Restricts all traffic across /api/* to 300 requests per 15-minute rolling window per IP.
  • Authentication Guard (authLimiter): Restricts /api/auth/login and /api/auth/register to 10 attempts per 15 minutes per IP.
  • Listing & Message Guard (creationLimiter): Caps listing creations and message transmissions to 25 requests per 15 minutes per IP to protect Cloudinary bandwidth and prevent database spamming.

4.4 Admin Bootstrapping & Privilege Escalation Defenses

Because public registration schemas forbid self-assigning the admin role, the system uses two secure elevation vectors:

  1. Initial Admin Seeding: authController.ts parses the INITIAL_ADMIN_EMAILS environment variable. Any registration matching this whitelist (e.g., seberbel@gmail.com) is automatically promoted to admin upon creation.
  2. Role Modification Endpoint: PATCH /api/auth/users/:id/role permits existing authenticated admins to promote or demote other users, with a hardcoded guard preventing an admin from accidentally stripping their own admin privileges.

05 Media Streaming & Cloudinary Memory Pipeline

5.1 The Ephemeral Storage Dilemma

Traditional web apps save uploaded files to local disk paths (e.g., /uploads). In containerized cloud environments (Docker, Railway, AWS ECS), this pattern is fundamentally broken:

  • Ephemeral Filesystems: When a container restarts, crashes, or is rescheduled across nodes, all local disk modifications are destroyed.
  • Multi-Instance Desync: If multiple API instances run behind a load balancer, an image uploaded to Node A cannot be served by Node B.
  • Solution: Injibara Market bypasses disk storage entirely, streaming image bytes directly from incoming TCP sockets to Cloudinary's global media storage.

06 Frontend Integration & State Synchronization

6.1 Centralized Axios Interceptor Architecture

The frontend isolates all network interaction within client/src/api/axiosClient.ts:

  • Request Interceptor: Inspects localStorage for injibara_market_token and injects the Authorization: Bearer <token> header on all outbound requests.
  • Session Expiration Interceptor: On HTTP 401 responses, the client automatically clears credentials (clearAuth()), alerts the user via a toast message, and forces a window redirect to /login.
  • Toast Deduplication: The notifyThrottled() helper prevents notification flooding during network disconnects by suppressing identical error toasts within a 5-second cooldown window.

6.2 Cold-Start Resilience Architecture

Because free/serverless cloud infrastructure sleeps after periods of inactivity, a naive user experience results in timeout failures during cold starts. Injibara Market implements four layers of cold-start fortification:

Layer Implementation File Mechanism
1. Proactive Wake-up Ping client/src/App.tsx On root component mount, sends a non-blocking background fetch('/healthz') to initiate server wake-up before the user navigates to catalog data.
2. Extended Timeout Window client/src/api/axiosClient.ts Global timeout increased from 15s to 60,000ms (60s) to allow cloud containers and TiDB nodes to complete cold-boot sequences without client termination.
3. Exponential GET Retry client/src/api/axiosClient.ts Idempotent GET requests experiencing network timeouts, connection drops, or 502-504 gateway errors are automatically retried up to 2 times with exponential delays (1.5s → 3s).
4. Resilient Fallback UI CustomerFeaturedListings.tsx, CategoriesPage.tsx Network failures display an explicit error alert with a manual Retry trigger rather than silently collapsing into a false "No products found" empty state.

6.4 State Flow & Component Synchronization

The application avoids heavy state management libraries, favoring explicit state mechanisms:

  • URL Search Parameters as State: In ProductsPage.tsx, active search queries, category filters, and location selections are mirrored into URL query parameters (useSearchParams), enabling shareable deep links and browser back-button navigation.
  • CustomEvent Synchronization: When a user favorites a product in ProductDetailPage, it writes to savedStorage.ts and fires window.dispatchEvent(new Event('saved_products_updated')). Global navigation components listen for this event and immediately update their badge counts.

6.5 Admin Broker Hub Engine

The Broker Hub (server/src/controllers/adminController.ts & client/src/pages/admin/BrokerHubPage.tsx) manages high-value brokered negotiations. Its core technical achievement is transactional message deduplication:

Admin Reply Deduplication Rule
Historically, when an admin replied to a buyer's inquiry, the naive message query generated a duplicate inquiry card in the dashboard. The current architecture groups messages into a unique key ${product_id}_${buyer_id}. Admin responses are folded directly into the conversation history of the original inquiry group, updating the latest_message_text and setting has_admin_reply = true without creating redundant pipeline items. Status changes and appointment dates are persisted directly to the broker_inquiries database table.

07 Containerization & DevOps Mechanics

7.1 Docker Compose Local Development Environment

The local container topology in docker-compose.yml coordinates three isolated container services:

  • mysql Service: Runs official MySQL 8.0 on host port 3307 (mapped to container 3306) with a recurring healthcheck pinging mysqladmin ping -h localhost.
  • api Service: Builds from api.Dockerfile. Configured with depends_on: mysql: condition: service_healthy to prevent Node startup race conditions before database socket availability.
  • client Service: Runs Vite development server exposing port 5173, bound to 0.0.0.0 host interfaces for external container access.

7.2 Dockerfile Multi-Stage Build Analysis

The production API image (docker/api.Dockerfile) utilizes multi-stage Docker build mechanics: 

# Multi-stage build in docker/api.Dockerfile
FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json ./
COPY server/package*.json ./server/
RUN npm ci --workspace=server
COPY server/ ./server/
WORKDIR /app/server
RUN npx prisma generate
RUN npm run build

FROM node:20-alpine AS runner
WORKDIR /app
COPY --from=builder /app/node_modules ./node_modules
COPY --from=builder /app/server/node_modules ./server/node_modules
COPY --from=builder /app/server/dist ./server/dist
COPY --from=builder /app/server/package.json ./server/package.json
EXPOSE 5000
CMD ["node", "server/dist/index.js"]

This pattern ensures compiler tooling, source TypeScript files, and intermediate build artifacts are discarded, leaving only compiled JavaScript and production runtime dependencies in the final deployment image.

7.4 Vercel Production Ingress

The frontend SPA is hosted on Vercel's global edge network. Client-side routing is enabled by vercel.json: 

{
  "rewrites": [
    { "source": "/(.*)", "destination": "/index.html" }
  ]
}

All HTTP requests entering Vercel's edge resolve directly to index.html, permitting React Router's browser history API to handle dynamic route mounting without generating HTTP 404s on page refresh.
